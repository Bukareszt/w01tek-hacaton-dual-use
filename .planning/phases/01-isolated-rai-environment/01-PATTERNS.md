### `experiments/wojtek_rai_v1/run.sh` (script, request-response subcommand dispatch)

**Analog:** `experiments/autonomous_architecture_ros2_v1/run.sh` (full file read, 55 lines)

**Header + self-containment pattern** (lines 1-18):
```bash
#!/usr/bin/env bash
# Entry point for the experimental agentic stack.  Self-contained on purpose:
# nothing outside this directory is configured to know about the experiment, so
# every path it needs is set up here.  See README.md.
set -euo pipefail
cd "$(dirname "$0")"
HERE="$PWD"
TRAINING="$(cd ../../training && pwd)"

# The training venv is the interpreter that has numpy/pytest/mujoco.  A
# worktree has no venv, so allow an explicit interpreter:
#   EXP_PY=/path/to/python ./run.sh test
PY="${EXP_PY:-$TRAINING/.venv/bin/python}"
[ -x "$PY" ] || command -v "$PY" >/dev/null 2>&1 || PY="python3"

# The experiment imports the training project (sim, policy runtime, planner);
# never the other way round.
export PYTHONPATH="$HERE:$TRAINING${PYTHONPATH:+:$PYTHONPATH}"
```
For `wojtek_rai_v1`, replace the `TRAINING`/`EXP_PY` interpreter-selection block with the RAI experiment's own `.venv` (D-03): `PY="$HERE/.venv/bin/python"`, and add the ROS-aware wrapper from RESEARCH.md Pattern 2/4 (source `/opt/ros/jazzy/setup.bash`, then the experiment's `ros_ws/install/setup.bash` if built, then `cd "$HERE"` before invoking Python) — this is the RAI-specific addition the sibling doesn't need since it has no venv of its own.

**Subcommand dispatch pattern** (lines 20-53, `case "${1:-}" in ... esac`):
```bash
case "${1:-}" in
  test)
    shift
    echo ">> wojtek_agent (python layer)"
    "$PY" -m pytest tests -q "$@"
    ...
    ;;
  build)
    shift
    command -v colcon >/dev/null 2>&1 || { echo "colcon not found: source a ROS 2 setup.bash first" >&2; exit 1; }
    exec colcon build --base-paths ros/src "$@"
    ;;
  *)
    echo "usage: run.sh {test|room|build} [args]"
    exit 1
    ;;
esac
```
`wojtek_rai_v1/run.sh` needs targets `install | build | test | agent | up | agent-topics` (D-05/D-16). `build` follows the sibling's `--base-paths` shape but points at `ros_ws` (D-09), and must run `vcs import` + `rosdep install` before `colcon build` (RESEARCH.md Pitfall 3). `agent`/`up`/`agent-topics` are new targets with no sibling precedent — they invoke `docker exec` against the running `wojtek_robot` container (RESEARCH.md Pitfall 4: env vars only apply if launched via `docker exec` into the already-running container, not a separate `docker run`), using the compose-override stack: `docker compose -f ../../ros/docker/compose.yaml -f docker/compose.override.yaml ...`.

**Colcon-outside-`ros/src` isolation comment** (lines 38-42, directly reusable rationale):
```bash
  build)
    # colcon build for this experiment's ROS packages only.  They live outside
    # ros/src so that ros/deploy.sh (which rsyncs ros/src to the robot) can
    # never ship them; that also means ros/sim.sh does not build them, hence
    # this target.  Run it in an environment that has ROS 2 sourced.
```
Copy verbatim (renaming `ros/src` → `ros_ws`) — this is the exact rationale D-09 states for `wojtek_rai_v1`.

## Shared Patterns

### Isolation boundary (applies to: `run.sh`, `README.md`, `docker/compose.override.yaml`, `ros/rai_interfaces.repos`, `tests/test_isolation_boundary.py`)
**Source:** `experiments/autonomous_architecture_ros2_v1/README.md` §"The isolation rules this experiment follows" (lines 39-63), `CLAUDE.md` §"Repository map and boundaries"
- Nothing outside `experiments/wojtek_rai_v1/` imports it.
- No shared build/test config (`ros/docker/compose.yaml`, `ros/sim.sh`, `ros/dev.sh`) is edited — only extended via the experiment's own override file.
- ROS packages (`rai_interfaces`, and later this experiment's own) live outside `ros/src/` in `ros_ws/`, unreachable by `ros/deploy.sh`'s `rsync ros/src/`.
- Behavior needed from existing code is added by extension (D-01's container reuse is analogous: extend via compose override, never edit the base compose/image).

### Secrets via root `.env`, sourced by the script that needs them (applies to: `run.sh`, `.env.example`, `config.toml`, `tests/test_no_secrets_in_config.py`)
**Source:** `ros/deploy.sh` lines 28-40 (verified this session)
```bash
# Secrets + local overrides (UBUNTU_PRO_TOKEN, optional RPI_HOST, ...).
if [ -f "${HERE}/.env" ]; then
    set -a; . "${HERE}/.env"; set +a
fi
```
`wojtek_rai_v1/run.sh` sources the repo-root `.env` (not an experiment-local one — D-11 explicitly rejects that) the same way, then passes the resulting env vars into the container via `docker exec -e VAR=...` or compose `env_file`/`environment` passthrough for the `agent`/`up` targets. `config.toml` never carries key fields (verified against upstream template — no key fields exist in the schema at all); keys arrive purely through this env-var path, matching `UBUNTU_PRO_TOKEN`'s existing precedent exactly.

### Guard-test structure: glob/parse + regex + diagnostic assert (applies to: all four `tests/` files)
**Source:** `training/tests/unit/test_job_scripts.py` (full file, 131 lines)
- Module-level compiled `re.compile(...)` constants with a comment above each explaining exactly what shape it matches and why.
- A `Path`-returning helper (`payloads()` / `tracked_config_files()`) that a `@pytest.mark.parametrize` or a plain loop consumes — no fixtures, no setup/teardown, no live process.
- Every assertion carries an f-string with the offending file name and the actual matched values, never a bare `assert`.
- Docstring at the top of the file states what this repository cares about and, just as important, what it deliberately does NOT check (mirrors the "how a dispatcher reads a declaration is not this repository's concern" framing) — for the RAI tests, the equivalent line is "this suite is model-free: no `rclpy`, no LLM key, no GPU" (FOUND-06).

### Compose-override-not-edit for container extension (applies to: `docker/compose.override.yaml`, `run.sh`'s `agent`/`up`/`build` targets)
**Source:** `ros/sim.sh` lines 111-119, `ros/dev.sh` lines 42-49 — both already select an additional compose file (`compose.mac.yaml`, `compose.gpu.yaml`) on top of the base `compose.yaml` depending on the host, proving the "stack more `-f` files, never edit the base" convention is already established in this repo, not a new pattern this phase introduces:
```bash
COMPOSE=(docker compose)
if [ "$(uname -s)" = "Darwin" ]; then
  COMPOSE+=(-f compose.yaml -f compose.mac.yaml)
elif docker info 2>/dev/null | grep -q 'Runtimes:.*nvidia'; then
  COMPOSE+=(-f compose.yaml -f compose.gpu.yaml)
fi
```
`run.sh`'s `agent`/`up`/`build`/`install` targets append `-f experiments/wojtek_rai_v1/docker/compose.override.yaml` to this same kind of array, on top of whatever `ros/dev.sh`'s own platform-detection already selected — i.e. `wojtek_rai_v1/run.sh` should replicate this exact `uname`/`docker info` branch, not assume Linux/no-GPU.

### `docker exec` into the already-running named container, not a separate `docker run` (applies to: `run.sh`'s `agent`/`build`/`agent-topics` targets)
**Source:** `ros/sim.sh` lines 193-231, `ros/dev.sh` line 52
```bash
exec docker exec -it ${DOCKER_ENV[@]+"${DOCKER_ENV[@]}"} wojtek_robot bash -c '
  source /opt/ros/${ROS_DISTRO:-jazzy}/setup.bash
  source /ros2_ws/install/setup.bash
  exec "$@"' _ "${CMD[@]}" ${EXTRA[@]+"${EXTRA[@]}"}
```
This is the exact mechanism RESEARCH.md's Pitfall 4 requires: `docker exec` against the named `wojtek_robot` container inherits its `ROS_DOMAIN_ID=42`/`RMW_IMPLEMENTATION`/`CYCLONEDDS_URI` environment; a fresh `docker run` would not. `wojtek_rai_v1/run.sh`'s `agent` target should follow this identical `docker exec wojtek_robot bash -c '...'` shape, adding the RAI venv's `source .venv/bin/activate` (or direct `.venv/bin/python` invocation) after the ROS setup sourcing, per RESEARCH.md Pattern 2.
