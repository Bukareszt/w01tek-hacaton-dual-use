  <read_first>

  </read_first>
  <decision>How `experiments/wojtek_rai_v1` becomes visible inside the running `wojtek_robot` container without either editing `ros/` or killing a running simulation.</decision>
  <context>
    D-02 says the experiment reaches the container through its own compose override, invoked as
    `docker compose -f ros/docker/compose.yaml -f <override> ...`, and that `ros/docker/` stays
    untouched. D-05 says `run.sh agent` assumes `ros/sim.sh` is already running.

    Planning-time finding that makes those two statements mechanically incompatible as written:
    neither `ros/sim.sh` nor `ros/dev.sh` has an extension point for extra compose files. Each
    builds its own argument array (`docker compose`, plus `-f compose.yaml -f compose.mac.yaml` on
    macOS or `-f compose.yaml -f compose.gpu.yaml` when an NVIDIA runtime is present) and then runs
    `up -d`. Docker Compose recreates a container whose desired service configuration no longer
    matches the running one. So:

    - Start the sim with `ros/sim.sh`, then have `run.sh` add the override — the container is
      recreated and the exec'd sim session dies.
    - Bring the container up with the override first, then run `ros/sim.sh` — the container is
      recreated without the mount.

    On a plain Linux host with no NVIDIA runtime the scripts fall through to a bare
    `docker compose`, which would honour the `COMPOSE_FILE` environment variable — but both target
    machines (the laptop and the aarch64 dev box) have NVIDIA runtimes, so that branch passes
    explicit `-f` flags and `COMPOSE_FILE` is ignored. It is not a reliable seam.

    This decision is `costly`, not `one-way`: it shapes every `run.sh` target in this phase and the
    four phases after it, but reversing it is a rewrite of `run.sh`, not a migration.
  </context>
  <options>
    <option id="option-a">
      <name>run.sh owns the container lifecycle (recommended)</name>
      <pros>
        Zero edits to ros/ — the literal letter of D-02, criterion 2's "no changes to ros/docker,
        ros/sim.sh or ros/src", and the CLAUDE.md experiments rule are all honoured. One container,
        the bind mount is always present, and the behaviour is identical on both machines. The
        experiment stays deletable with one rm -rf.
      </pros>
      <cons>
        run.sh must replicate the platform branch that ros/sim.sh and ros/dev.sh already contain
        (uname -s = Darwin, or `docker info` reporting an nvidia runtime) and, for `run.sh up`,
        exec the same session command ros/sim.sh execs. That is duplicated logic which can drift if
        ros/sim.sh changes. Criterion 2 is then read as "the sim session started through the
        experiment's own up target", not "ros/sim.sh literally started it".
      </cons>
    </option>
    <option id="option-b">
      <name>Add a generic extra-compose-file hook to ros/sim.sh and ros/dev.sh</name>
      <pros>
        One shared, experiment-agnostic seam (an environment variable appended to the COMPOSE array
        in both scripts) removes the duplication entirely and lets ros/sim.sh literally start the
        sim with the experiment mounted, satisfying criterion 2 word for word. Arguably the
        "behaviour added by extension, not edit" rule the sibling experiment states.
      </pros>
      <cons>
        It is still a change to two files under ros/, which criterion 2 and D-02 forbid outright,
        and it makes a production entry point carry a hook that exists only for an experiment. It
        also has to land on both machines before either can be verified.
      </cons>
    </option>
  </options>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PyPI / astral.sh → the container | Third-party code and a downloaded `uv` binary cross into the dev container at `run.sh install` time |
| host shell → `wojtek_robot` container | `run.sh` issues `docker compose` and `docker exec` against a privileged, host-networked container |

| running ROS 2 graph → RAI process | The RAI process joins the same DDS domain as the simulation and the policy control loop |
